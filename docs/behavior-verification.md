# Behavioral verification

Behavioral verification is opt-in for each project. Copy the drafts in `templates/verification/`, adapt them to the real project and register them in `.harness-verification.json`; do not install them automatically. The manifest is the authoritative feature index, and its references point to existing requirement or acceptance IDs. A missing manifest or `enabled: false` leaves existing checks unchanged; an invalid enabled manifest fails verification. `harness behavior validate --project PATH` is read-only and returns zero for valid, missing, or disabled definitions and nonzero for invalid input.

A guide describes launch, readiness, isolation, user actions, independently observable results, and cleanup. A feature map links journeys to existing requirements and tests. Select affected features in the task contract; `harness behavior check --project PATH --features ID...` is an ordinary read-only acceptance command, not an automatic requirement for every feature. A full maintenance pass explicitly selects all features and reports any missing evidence; explain exclusions and manual or blocked invariants rather than inventing passes.

Start with `harness behavior begin --project PATH --feature ID --evidence-dir PATH`; choose a new, ignored directory within the project, outside protected locations. Capture an actual journey there, preserve evidence during cleanup, and record a bounded report with `harness behavior record --project PATH --attempt ID --report FILE`. The report format is defined in `schemas/behavior-verification.schema.json`; the attempt identity is in the run-owned receipt. Use a new attempt when source, definitions, installed build, device, session, or configuration changes. A passing report requires matching known source and runtime build identities, readiness, actions, cleanup, and artifacts. Failed, blocked, and inconclusive reports require a reason. Commands return nonzero for rejected input or missing current evidence.

The check revalidates run, source, definitions and artifact hashes without starting an app or replaying actions. Hashes establish integrity, not the truth of a claimed observation. Record actual input and independent output, the exact build and test environment, and cleanup of owned fixtures; preserve unrelated state. Review packets summarize available current-run evidence and artifact references. Findings can optionally label evidence `reproduced`, `source_analysis`, or `unverified_concern`, and include `repro_command`, `expected`, and `actual`. Keep concerns visible when reproduction is unsafe or unavailable; labels do not alter review or approval gates.

For critical assumptions, record a small executable reproduction when safe and document what it proves and does not prove. For benchmarks, compare equivalent configurations and successful, nonzero work; report samples, variance, environment, and uncertainty, and mark fast errors, mismatched work, or noise inconclusive. Turn recurring feedback into a linked, non-skipped passing regression test when feasible; otherwise keep it explicitly manual or blocked. These practices create no recurring jobs or device automation, and a template remains a draft until a real journey and its evidence survive cleanup.
